# harness-audit — Four pillars + executable rubric + self-correction loop

## Paradigm

The audit is not a static report a human reads and executes — it is an **executable rubric** that a loop converges against. Loop Design in one line: goal → rubric (every criterion checkable by command) → independent verifier → memory that compounds. *"Garbage rubric + great model = a confidently wrong loop."* The human-readable report derives FROM the rubric, never the other way around.

The model is the horse; the harness is the saddle. Models change every few months — the harness stays. That is why the artifact of value is the rubric and the role conventions, not any one model.

See [WHITEPAPER.md](https://github.com/andrami-pro/harness-audit/blob/main/WHITEPAPER.md) for the full rationale, benchmarks, and theory.

## When to invoke

Run this when **any** of these is true:

- Starting a new agent session in an unfamiliar repo and you want to know how mature its harness is
- The user mentions: `AGENTS.md`, harness, preflight, subagent, orchestrator, reviewer, self-improving loop, loop design, rubric, verifier
- The user asks to "make this repo portable" / "set up for Claude Code and Codex"
- Before a multi-week project — invest 30 minutes in the harness so the model becomes interchangeable

## What I produce

1. **Audit report** — four-pillar checklist with ✓/✗/partial per item + **loop-readiness grade L0–L3**
2. **`harness-rubric.md`** — executable rubric: every item carries a `Check:` command + threshold + current state (format in [rubric-template.md](rubric-template.md))
3. **Stack-tailored plan** — concrete files/commands matching the detected stack; every phase has a done-criterion + stop condition
4. **Adversarially verified findings** — a fresh-context subagent re-runs sampled checks before delivery (protocol in [verifier-protocol.md](verifier-protocol.md))

## Workflow

### Step 0 — Existing harness? Upgrade in place, never regenerate

Check first: does `harness-rubric.md` exist, or `.claude/workflows/develop-phase.js`, or an `AGENTS.md`
with `Check:` rows already in it? If any of those is present, this is a **re-audit**, not a fresh install
— run the rest of this skill in upgrade mode:

- **Re-run every existing `Check:` command** and refresh its current state. Do not discard rows whose
  check still passes.
- **Annotate changed rows with `(run N)`**, N = one past the highest run number already in that row's
  history (start at `run 2` if the row carries none yet). A row whose state didn't change keeps its last
  annotation — `run N` marks a re-verification that moved the needle, not every keystroke.
- **Add criteria the rubric doesn't have yet**: the Graphify item (P1-8), a loop-existence check per loop
  this project has actually run (mirror the README's honesty rule — a loop with no run in
  `docs/harness-dev/loop-runs/` gets no row), a `LEARNINGS.md` convention check if any skill loop has
  run, and the four Pillar-4 rows for the memory's shape on disk (decision lifecycle, postmortems, doc
  word budgets, the mutation-proven gate) — the first two flagged ⚠ when their directory is absent.
- **Modernize obsolete criteria** in place — e.g. a `CodeGraph` reference becomes the Graphify check —
  rather than leaving a stale row next to a new one that says the same thing.
- **Never clobber a rule the human promoted.** Any `AGENTS.md` line the human wrote or explicitly approved
  (not auto-generated by a previous audit run) is untouchable: read the file, propose additions as a diff,
  never overwrite the file wholesale. The same holds for `.claude/workflows/develop-phase.js` — **patch**
  it (targeted edits: add a phase, bump a model, add a criterion) instead of regenerating it from the
  template in Step 4b, which would silently drop any project-specific customization a prior session added.
- **Re-score the loop-readiness grade (L0–L3)** and the memory grade (M1–M5) from the refreshed state —
  they are derived values, not carried over from the last run.
- **Report as a delta**, not a fresh audit: what was already ✓ and stayed ✓, what moved, what's new. A
  re-audit that reads like a first audit throws away the project's history for no reason.

If none of those signals is present, this is a first audit — proceed to Step 1 as normal.

### Step 2 — Audit the four pillars

#### Pillar 1 — Harness in code (files at repo root + folder conventions)

| Item | What to check | How |
|---|---|---|
| Portable entry point | `AGENTS.md` exists at root | `test -f AGENTS.md` |
| AGENTS.md not bloated | ≤ 200 lines | `wc -l < AGENTS.md` |
| Harness-specific delta | `CLAUDE.md` / `.cursorrules` / Antigravity equivalent, short (~40–60 lines), points to AGENTS.md | `wc -l` + `grep -i agents.md` |
| Preflight script | Single command that runs all health checks | `grep -E '"(preflight\|verify\|check)"' package.json` (or `Makefile`, `justfile`, etc.) |
| Memory exists | Convention for logging progress (sprint log, ADR folder, decision log, memory dir) | `find docs/ .claude/ -iname "*log*" -o -iname "*decision*" -o -iname "*adr*" -o -iname "*memory*" 2>/dev/null` — existence only; **quality is graded in Pillar 4** |
| Task tracking | Tasks file or external tracker reference | `test -f TASKS.md` or check `AGENTS.md` for Linear/Jira link |
| Graphify graph exists | `graphify-out/graph.json` exists — a full AST-parsed structural graph so critics/scorer query structure instead of burning context on grep | `test -f graphify-out/graph.json && echo PASS \|\| echo FAIL` — FAIL is **blocking**: if the `graphify` CLI is missing, the plan MUST include installing it (`uv tool install graphifyy`, fallback `pipx install graphifyy` / `pip install graphifyy`) as a Phase 1 step; if the CLI exists but no graph, bootstrap with `graphify extract . --code-only` |

#### Pillar 2 — Role separation (multi-agent) + verifier independence

| Item | What to check | How |
|---|---|---|
| Subagents folder | `.claude/agents/` (or equivalent) exists with at least one role definition | `ls .claude/agents/*.md 2>/dev/null` |
| Reviewer present | A subagent that audits diffs against rules | `grep -l -i "reviewer\|review.*diff" .claude/agents/*.md 2>/dev/null` |
| Reviewer independence | Reviewer receives ONLY diff + rules — never the implementer's reasoning or chat context | read reviewer.md: inputs must be artifacts (diff, files, rubric), not conversation |
| Reviewer refutes, not confirms | Reviewer prompted to find reasons to REJECT, with evidence per criterion (PASS/FAIL + quote) | `grep -i "refut\|reject\|evidence\|evidencia" .claude/agents/reviewer*.md` |
| No self-approval | AGENTS.md documents that the implementer never approves its own diff | `grep -i "self.approv\|auto.aprob\|reviewer" AGENTS.md` |
| Skills (personas) | A skills folder for domain personas (PM, dev, UX, etc.) | `ls .claude/skills/*/SKILL.md 2>/dev/null` |
| Multi-harness portability | Same role conventions discoverable for Codex/Cursor (AGENTS.md mentions roles abstractly) | `grep -i "orchestrat\|implement\|review" AGENTS.md` |
| Model line-up independence (D25, P2-8) | If a `model-lineup.json` exists (global or project), the reviewer role's model does not share a family with the implementer role's model | `node "${CLAUDE_PLUGIN_ROOT}/scripts/model-lineup.js" resolve --target claude --global ~/.agents/model-lineup.json --project .agents/model-lineup.json; echo $?` — `0` = independent, `2` = HARD violation (not confirmable); no lineup file at all is N/A, not FAIL. The script ships with the plugin, not with the audited repo, so the `${CLAUDE_PLUGIN_ROOT}` prefix is mandatory — a bare relative path exits 1 and reads exactly like "no lineup" |

#### Pillar 3 — Automatic verification

| Item | What to check | How |
|---|---|---|
| Lint | Linter configured + `lint` script | Match `eslint.config.*`, `.eslintrc.*`, `.flake8`, `ruff.toml`, `clippy.toml`, etc. |
| Typecheck | Typechecker available (only if typed lang) | `tsc --noEmit` script, `mypy`, `pyright`, `cargo check` |
| Tests | Test runner installed + `test` script | Detect Vitest/Jest/Playwright/pytest/cargo test/go test/rspec |
| Test quality (anti-false-convergence) | Tests contain real assertions — they would FAIL if the code broke. Trivial always-green tests satisfy the letter of "tests pass" while lying to the loop | open 1–2 test files: assertions on behavior, not `expect(true)`; flag suites with 0 assertions |
| Pre-commit hook | Hook framework installed | `test -f lefthook.yml` OR `.husky/` OR `.pre-commit-config.yaml` OR `pre-commit` in git hooks |
| CI workflow | At least one CI pipeline runs preflight on PR | `ls .github/workflows/*.yml` or equivalent |
| Self-improving loop | AGENTS.md/CLAUDE.md instructs reviewer to propose new rules | `grep -i "self.improv\|propose.*rule\|update.*agents.md" AGENTS.md CLAUDE.md 2>/dev/null` |
| Secret-scan gate | A write-time or pre-commit check catches credential patterns (`sk-`, `ghp_`, `AKIA`, PEM blocks) before they land in tracked files | inspect hook config (`hooks/hooks.json`, lefthook, pre-commit) for a secret scanner — this plugin ships one (`secret-scan.js`) |
| Destructive-command guard | Agent sessions cannot run `rm -rf` against root/home, `git checkout --force`, or `git clean -fdx` unchecked | inspect hook config for a Bash pre-execution guard — this plugin ships one (`destructive-guard.js`) |
| No-verify blocked | `git commit/push --no-verify` is rejected, so the pre-commit gate cannot be silently bypassed | `grep -rE "no.?verify" hooks/ .husky/ lefthook.yml 2>/dev/null` — this plugin ships `block-no-verify.js` |
| Loop-hygiene guard | A tool-call hook counts consecutive byte-identical calls (same tool, same canonical arguments) and injects an escalating reminder at 3/5/8 — advisory, never a deny, so a model stuck re-running the same grep is told so instead of burning the budget | inspect hook config for a repeat-call guard — this plugin ships `repeat-tool-guard.js` (PreToolUse, matcher `.*`) |

#### Pillar 4 — Loop design (rubrics + continuous memory)

| Item | What to check | How |
|---|---|---|
| Executable done-rubric | `harness-rubric.md` exists, or AGENTS.md defines done-criteria as `Check:` commands with thresholds | `test -f harness-rubric.md` or `grep -c "Check:" AGENTS.md` |
| Preflight machine-readable | Preflight exits non-zero on failure and prints a parseable summary (a loop can read it) | run preflight; inspect `$?` and output structure |
| Stop conditions | Agent/skill definitions include iteration limits or escalation rules ("until X OR N attempts") | `grep -riE "stop\|máximo\|max.*(iter\|attempt)\|escalat" .claude/agents/ .claude/skills/ 2>/dev/null` |
| Memory maturity M1–M5 | Grade the BEST memory artifact against the progression scale below | read 2–3 memory/ADR files and classify |
| Memory consulted before acting | AGENTS.md/CLAUDE.md instructs agents to READ memory before starting work, not only write after | `grep -iE "l[eé]e.*memoria\|read.*memory\|consult" AGENTS.md CLAUDE.md` |
| Memory compaction policy | Size budget + dedup/merge rule documented (unbounded memory = bloat that degrades recall) | `du -sh` memory dir + `grep -iE "compact\|destil\|distill\|merge\|l[ií]mite\|limit" AGENTS.md` |
| Memory distilled from session telemetry | An offline analyzer reads past session logs, correlates each failure with the fix that *worked*, and writes distilled corrections (jumps M1→M3 in one step — see the success-correlation note below) | `grep -riE "success.correlat\|session.*log\|\blearn\b" scripts/ .claude/ package.json pyproject.toml 2>/dev/null` — usually absent; this is M4→M5 maturity, so flag ⚠ (aspirational), not ✗ (basic gap) |
| Auto-writes don't clobber curated memory | If any tool auto-writes to `memory/`/`AGENTS.md`/`CLAUDE.md`, it fences its output in delimited markers so hand-curated content survives a re-run | `grep -rE "<!--.*(start\|end).*-->" memory/ AGENTS.md CLAUDE.md CLAUDE.local.md 2>/dev/null` — N/A if nothing auto-writes memory |
| Decision lifecycle | Decisions live under `proposed/ implemented/ rejected/` so status is the path, and every implemented note carries `## Alternatives considered` — a decision recorded without what it beat invites re-litigation | `test -d docs/decisions/implemented && grep -rL "## Alternatives considered" docs/decisions/implemented/ \| wc -l` → 0 — usually absent; flag ⚠ (aspirational), not ✗ |
| Postmortems name the gap | Each postmortem has a section on why the safety nets missed it and which guardrail was added, not only the fix | `ls docs/postmortems/*.md 2>/dev/null \| xargs -r grep -Li "why the safety nets missed it" \| wc -l` → 0 — usually absent; flag ⚠ (aspirational), not ✗; never fabricate incidents |
| Doc word budgets | Standing docs (AGENTS.md, architecture, testing policy) have a word ceiling in `docs/doc-budgets.json`; generalizes the ≤ 200-line AGENTS.md row | `node "${CLAUDE_PLUGIN_ROOT:-.claude}/scripts/check-doc-budgets.js" --manifest docs/doc-budgets.json; echo $?` → 0 (exit 2 = no manifest = FAIL, fix cost low) |
| Gate proven by mutation | A versioned script breaks a component, asserts the preflight exits non-zero, and reverts — the proof the anti-false-convergence row asks for, kept where the next person can re-run it | `test -f scripts/preflight-mutation.sh && sh scripts/preflight-mutation.sh >/dev/null 2>&1; echo $?` → 0 |

**Memory maturity scale** (continual-learning progression — grade by what the notes ARE, not how many):

- **M1 Fail** — raw failure notes, guesses, duplicates ("tried X, didn't work")
- **M2 Investigate** — notes explain WHY something failed — a postmortem's "why the safety nets missed it" section is M2 evidence
- **M3 Verify** — facts tagged `[VERIFIED]` / `[UNVERIFIED]` with the check that proved them
- **M4 Distill** — verified facts compressed into general rules ("when X, always Y") — an implemented decision note with `## Alternatives considered`, and a postmortem whose guardrails section names the rule it added, are M4 evidence
- **M5 Consult** — rules are actually read before acting (instruction exists + evidence of use, e.g. references in recent commits/ADRs)

> **Success-correlation shortcut (M1→M3).** The highest-signal way to climb from raw failure notes (M1) to verified facts (M3) is *not* hand-annotation — it's to correlate each failed action with the action that later **fixed** it: "`Read foo/X.java` failed → `Read bar/X.scala` succeeded ⇒ *X lives in bar/, not foo/*." The fix that worked IS the verification. An offline distiller (reference impl: headroom `learn`) automates this from agent session logs and writes it, marker-fenced, to the agent-native canonical file (`AGENTS.md` / `CLAUDE.local.md` / `GEMINI.md`) — the same portability principle as Pillar 1. Keep the human in the outer loop: default to the gitignored personal file + dry-run (propose, don't auto-merge).

### Step 3 — Output the audit report

Use exactly this format so it's machine-readable for follow-up plans:

```markdown
# Harness audit — <project name>

**Stack:** <primary>, <secondary>, <package manager>, <CI provider>
**Maturity:** <0-4> / 4 pillars complete · **Loop-readiness: L<0-3>** · Memory: M<1-5>

## Pillar 1 — Harness in code  [✓ N/M items]
- ✓ <item> — <path or evidence>
- ✗ <missing item> — <impact>
- ⚠ <partial item> — <what's incomplete>

## Pillar 2 — Multi-agent roles + verifier  [✓ N/M items]
…
## Pillar 3 — Verification  [✓ N/M items]
…
## Pillar 4 — Loop design  [✓ N/M items]
…

## Anti-patterns detected
- <e.g., AGENTS.md is 450 lines — bloated, will degrade context>
- <e.g., reviewer sees implementer's reasoning — self-critique in disguise (loses the independent-verifier advantage)>
- <e.g., memory is M1: 40 failure notes, no verified facts, no rules>

## Risks if shipped as-is
- <e.g., model lock-in, silent regressions, confidently wrong loop on a garbage rubric>
```

**Loop-readiness grades:**

- **L0** — no automatic verification: every change needs human eyes
- **L1** — manual verification: lint/tests exist but scattered, no single gate
- **L2** — single machine-checkable preflight gate: a loop can iterate against it
- **L3** — closed loop: executable rubric + independent verifier + consulted memory (Pillar 4 substantially ✓)

### Step 4 — Generate the stack-tailored plan (with stop conditions)

For every ✗ or ⚠ item, propose a concrete fix using the stack's idioms (recipe table below). The plan must be actionable — file paths, commands, dependency versions — not generic advice. **Every phase MUST carry:** (a) a done-criterion checkable by command, (b) an iteration limit, (c) an escalation rule ("if not converged after N attempts, stop and report blockers to the human"). A plan phase without a stop condition is an infinite loop of cosmetic changes waiting to happen.

| Stack | Preflight runner | Pre-commit hook | Test runner | E2E | CI |
|---|---|---|---|---|---|
| **Node + pnpm** | `tsx scripts/preflight.ts` via `pnpm preflight` | lefthook (Go binary, fast) | Vitest | Playwright | GitHub Actions |
| **Node + npm/yarn** | `tsx scripts/preflight.ts` | husky + lint-staged | Vitest / Jest | Playwright | GitHub Actions |
| **Node + bun** | `bun scripts/preflight.ts` | lefthook | bun test | Playwright | GitHub Actions |
| **Python + poetry** | `poetry run python scripts/preflight.py` | pre-commit framework | pytest | Playwright (python) | GitHub Actions |
| **Python + uv** | `uv run python scripts/preflight.py` | pre-commit | pytest | Playwright | GitHub Actions |
| **Rust + cargo** | `cargo xtask preflight` or `just preflight` | pre-commit + cargo-husky | `cargo test` | — | GitHub Actions |
| **Go** | `make preflight` or `task preflight` | lefthook | `go test ./...` | — | GitHub Actions |
| **Flutter** | `dart run tool/preflight.dart` | lefthook | `flutter test` | `flutter drive` / `patrol` | GitHub Actions |
| **Ruby on Rails** | `bin/preflight` | overcommit | RSpec / minitest | Capybara | GitHub Actions |

Preflight checks to always include: (1) AGENTS.md exists and ≤ 200 lines, (2) typecheck, (3) lint, (4) schema/config validation if runtime config exists, (5) domain-specific invariant if any, (6) doc word budgets when `docs/doc-budgets.json` exists. Preflight must exit non-zero on any failure — it is the loop's gate, not a log.

### Step 4a — Resolve the model line-up (D25)

Before emitting `develop-phase.js` in Step 4b, resolve which model plays which role instead of assuming
the hardcoded Opus/Fable/Sonnet names below. The line-up is a project-portable file
(`~/.agents/model-lineup.json`, harness-neutral — same schema `install.sh --lineup` reads), not a string
baked into this skill.

1. **Look for a line-up.** Resolve it with the script that ships with the plugin — `${CLAUDE_PLUGIN_ROOT}`
   is mandatory (same convention as the `loop-stats.js` call in `/session-review`): the script lives with
   the plugin, not with the repo being audited, so a bare relative path exits 1 and is indistinguishable
   from "this project has no line-up".
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/scripts/model-lineup.js" resolve --target claude \
     --global ~/.agents/model-lineup.json --project .agents/model-lineup.json
   ```
2. **Nothing found?** Propose the shipped `defaults` block (§Esquemas, D25 — Opus implementer, Fable
   reviewer/scorer/architect/judge, Sonnet orchestrator/preflight/critic) as this project's line-up, and
   **write `~/.agents/model-lineup.json` only with the human's consent**: "No model-lineup.json exists yet.
   Set one up globally with these defaults (Opus implementer / Fable reviewer / Sonnet preflight)?" A no
   means Step 4b uses the hardcoded table below for this run only — nothing gets written.
3. **HARD guardrail (D25a, never confirmable).** If resolution exits `2` — the reviewer and implementer
   share a model family — report the exact reason `model-lineup.js` printed and stop. Do **not** emit
   `develop-phase.js` with a self-reviewing pair, and do not ask the human to override this: there is no
   override.
4. **SOFT guardrail (D25b, confirmable per project).** If the resolution reports a `softViolations` entry
   (`model-lineup.js`'s `KNOWN_INVARIANTS` today ships one: it flags the role this repo retired its
   cheapest, fastest tier from back on 2026-07-02), use **AskUserQuestion** to ask exactly what the
   violation names, verbatim from `softViolations[].message`. A yes writes the exception into this
   project's `.agents/model-lineup.json`
   (`confirmedExceptions[]`, via `node "${CLAUDE_PLUGIN_ROOT}/scripts/model-lineup.js" record-exception`) — it never edits
   `validate.js` or any global invariant. A no means: stop and let the human fix the line-up instead of
   proceeding with an unconfirmed contradiction.
5. **Unknown model id?** `unknownModels` in the output is a warning, not a blocker — note it in the audit
   report and continue.
6. **Re-stamp the audited project's own agent role files.** `resolveLineup()`'s output already carries a
   `stamp` value per role — the exact string `install.sh --lineup` writes into a frontmatter `model:`
   field. Apply that same value here, because this is the one path `install.sh` cannot reach: a project
   that received harness-audit via `/plugin marketplace add` + `/plugin install` never runs `install.sh`,
   so without this step its own `.claude/agents/*.md` would keep whatever `model:` they were created with
   forever, no matter what the human's line-up says. For every file in the audited project's
   `.claude/agents/` (or the harness's equivalent folder) whose `name:` frontmatter matches a role in
   `model-lineup.js`'s `ROLES` list (`implementer`, `reviewer`, `orchestrator`, `preflight`, `scorer`,
   `critic`, `judge`, `architect`) and that role is present in `resolved`, edit that file's `model:` line to
   `resolved[role].stamp`. Skip a role absent from `resolved` (nothing configured for it — leave the file
   alone) and a file whose `name:` matches nothing in `ROLES` (a project-specific agent keeps whatever
   `model:` it already has; this step only re-stamps roles it can identify by name). Only reach this step
   once step 3 raised no HARD violation and step 4's SOFT violations, if any, are confirmed or the project
   line-up already carries the exception — never re-stamp under an open, unresolved contradiction. This
   applies identically regardless of which branch got you here: a line-up step 1 found already in place, or
   one step 2 just wrote with consent — existing or fresh, the project's own agents end up carrying it.
7. Carry the resolved `{role: model}` map into Step 4b instead of the hardcoded Opus/Fable/Sonnet names.
   Map roles to seats: `implementer` → Implementer, `reviewer` → Reviewer, `preflight` → Preflight. The
   line-up has no scout or analyst role: the Analyst takes the implementer's model, and the Scout takes the
   cheapest tier the project allows (`haiku`; use `sonnet` where the line-up retired Haiku — the D25b
   invariant covers the `preflight` role, not this read-only seat, but a project that retired the tier
   usually meant it everywhere).

### Step 4b — Emit the model-by-role develop-phase workflow (ALWAYS)

**This step is mandatory for every audit**, regardless of project size or maturity. Write `.claude/workflows/develop-phase.js` at the repo root using the line-up resolved in Step 4a (fallback: Scout=Haiku → Analyst=Opus → Implementer=Opus → Reviewer=Fable,
then the gate on Sonnet — the table below). Without model differentiation the loop degrades to self-critique-level accuracy; with an independent reviewer it catches materially more defects before merge. *(Provenance: the often-cited ~62% → ~89% figures are directional targets — not reproduced independently here. A reproducible A/B is planned: see `benchmarks/` (TODO) and WHITEPAPER §8.1. Until then, treat the gap as qualitative, not measured.)*

**Model assignment rationale (fallback lineup absent a resolved `model-lineup.json`: Opus 4.8 / Fable 5 / Sonnet 5 — a role/cost-fit heuristic, pending the benchmark above):**

| Role | Model class | Why |
|------|-------------|-----|
| Orchestrator | Mythos tier (e.g. Fable 5) | Designs the loop, owns the rubric, manages memory across sessions |
| Scout | fast/cheap (e.g. Haiku 4.5) | Reads the repo and returns a ≤ 400-word brief — retrieval, not judgement. Read-only |
| Analyst | workhorse frontier (e.g. Opus) | Verifies the brief and returns a ≤ 300-word plan; can stop the run on a blocker before the implementer spends anything. A Mythos-tier model rarely pays off in this seat: one call per task, and on the public indices we checked the quality gap over a frontier-cheap model is smaller than the price gap |
| Implementer | workhorse frontier (e.g. Opus 4.8) | Strong code generation at sustainable cost for the 80% of the work |
| Reviewer | Mythos tier (e.g. Fable 5) | An independent reviewer beats self-critique (directional; numbers pending the benchmark above) — and a *different family* than the implementer, on purpose (cross-family review reduces shared blind spots). May be a non-Anthropic model reached through the Step 4c bridge |
| Preflight checks | mid/fast (e.g. Sonnet 5) | Command execution + result parsing — cheap, fast, reliable |
| Complex security review | Mythos tier, extended thinking | Use only for high-criticality phases: injection testing, threat modeling |

> The model *classes* matter more than any specific name. Substitute the equivalent tier in whatever harness you run (Claude Code / Codex / Cursor). The point is role-differentiated capability — and an implementer/reviewer split across model families — not a fixed lineup.

**Generic template to write** (adapt the PRD path and project-specific rules to the stack detected in Step 1):

```js
export const meta = {
  name: 'develop-phase',
  description: 'Scout → Analyst → Implementer → Reviewer adversarial loop against harness-rubric.md, then a final Preflight gate.',
  phases: [
    { title: 'Scout',     detail: 'Gather context into a short brief (read-only)', model: 'haiku' },
    { title: 'Plan',      detail: 'Turn the brief into a short plan, or stop on a blocker', model: 'opus' },
    { title: 'Implement', detail: 'Write code against the PRD + brief + plan', model: 'opus' },
    { title: 'Review',    detail: 'Find reasons to reject (independent verifier > self-critique)', model: 'fable' },
    { title: 'Preflight', detail: "Run the project's preflight gate", model: 'sonnet' },
  ],
}

// args: { task, phase?, maxIter?, preparer?, analystModel?, reviewerModel? }
//   preparer: false skips Scout + Plan (a trivial task: the implementer explores on its own).
//   reviewerModel: a native alias ('fable') or a provider-qualified id ('openrouter/<vendor>/<model>'),
//   the latter routed through scripts/external-review.sh (Step 4c) because agent() only dispatches Anthropic models.
const task     = args?.task    ?? 'implement the active task in TASKS.md or equivalent'
const phaseN   = args?.phase   ?? null
const maxIter  = args?.maxIter ?? 5
const preparer = args?.preparer !== false

// Replace these defaults with the line-up resolved in Step 4a.
const MODELS = {
  scout: 'haiku',
  analyst: args?.analystModel ?? 'opus',
  implementer: 'opus',
  reviewer: args?.reviewerModel ?? 'fable',
  preflight: 'sonnet',
}

// Adapt this path to the project's PRD convention (detected in Step 1)
const prdHint = phaseN
  ? `Reference PRD: docs/prd/prd-phase-${phaseN}-*.md`
  : 'Active phase: see TASKS.md or equivalent'

log(`Task: "${task}" · max ${maxIter} iter · ${preparer ? `Scout=${MODELS.scout} · Analyst=${MODELS.analyst} · ` : ''}Implementer=${MODELS.implementer} · Reviewer=${MODELS.reviewer}`)

// Every early exit is a 'blocked' handoff, never an exception: the caller reads one contract.
const stop = (summary, blocker, iterations = 0, evidence = []) => ({
  task, iterations, approved: false, preflightPassed: false,
  handoff: { status: 'blocked', summary, evidence, blocker },
  nextStep: blocker,
})
// agent() returns null when a seat dies (network, API) or the human skips it: never interpolate that
// "null" into the next prompt, never call .trim() on it.
const crash = (who, iteration) => stop(
  `The ${who} returned nothing in iteration ${iteration} (seat died or was skipped)`,
  'Run git status before re-running: the implementer may have left half-finished changes', iteration)

// D25a at run time: reviewer and implementer must not share a model family, or "independent review" is
// self-critique. Crude on purpose (an alias, or the vendor segment of a provider-qualified id);
// scripts/model-lineup.js is the full check.
const familyOf = (m) => {
  const id = String(m).replace(/^[^/]+\//, '')
  const claude = id.match(/(?:^|\/)(?:claude-)?(opus|fable|sonnet|haiku|mythos)/)
  return claude ? `claude-${claude[1]}` : id.split('/')[0]
}
if (familyOf(MODELS.reviewer) === familyOf(MODELS.implementer)) {
  return stop('Reviewer and implementer share a model family',
    `Both resolve to "${familyOf(MODELS.reviewer)}" — change reviewerModel to another family (D25a has no override)`)
}

// Scout and Plan run once, outside the loop. They are a cost optimisation, not a gate: if a seat dies the
// run continues without it and the implementer explores on its own.
let brief = '', plan = ''
if (preparer) {
  phase('Scout')
  brief = await agent(
    `You are the scout of a development loop. Read-only: do not edit or create files, run nothing that writes.
If a code graph exists (graphify-out/graph.json), query it first (\`graphify query "<question>"\`); otherwise use Grep/Glob.
Open raw files only afterwards, for specific lines.
Read only what is relevant of: memory/, ${prdHint}, TASKS.md or equivalent.
TASK: ${task}
Return a brief of at most 400 words, no filler:
- Relevant files: path:line + one sentence (what it does, why it matters)
- Rules from the PRD and project docs that apply (short quotes)
- Existing tests in that area (paths)
- Open questions or ambiguities a human should settle
Do not propose the solution.`,
    { model: MODELS.scout, label: 'scout', phase: 'Scout' }
  ) ?? ''
  if (!brief) log('⚠ Scout returned nothing — the implementer explores on its own')

  if (brief) {
    phase('Plan')
    plan = await agent(
      `You are the analyst of a development loop. Read-only: edit nothing.
You receive the task and a scout's brief. Verify in the code only what you doubt in the brief
(open the cited files; query the code graph before grepping).
TASK: ${task}
BRIEF:
${brief}
Return a plan of at most 300 words:
1. Ordered steps, each with the file it touches.
2. Tests to add or adjust (the reviewer demands regression coverage when existing logic changes).
3. Risks, and what NOT to touch (out of the PRD's scope). Every risk you name is binding on the implementer.
If the brief is not enough or an ambiguity blocks the work, the FIRST line is "BLOCKER: <reason>" and nothing else.
No full code: the implementer writes it.`,
      { model: MODELS.analyst, label: 'analyst', phase: 'Plan' }
    ) ?? ''
    if (!plan) log('⚠ Analyst returned nothing — the implementer works from the brief alone')
    else if (plan.trimStart().startsWith('BLOCKER:')) {
      log('⛔ The analyst found a blocker — stopping before the implementer runs')
      return stop('The analyst needs a decision before implementation', plan.trim(), 0, [brief])
    }
  }
}
const context = brief
  ? `A scout and an analyst prepared the context: start from it, open the original only when something does not add up
or to write code, and do not re-explore the repo. The plan's risks are binding.
BRIEF:
${brief}
${plan ? `\nPLAN:\n${plan}\n` : ''}
Read: harness-rubric.md, .claude/agents/implementer.md.`
  : `Read: memory/, ${prdHint}, harness-rubric.md, .claude/agents/implementer.md.`

let approved = false, lastImpl = '', lastReview = '', iteration = 0

while (!approved && iteration < maxIter) {
  iteration++
  log(`── Iteration ${iteration}/${maxIter} ──`)

  phase('Implement')
  const correctionCtx = iteration > 1
    ? `\n\n⚠ Reviewer REJECTED. Reasons:\n${lastReview}\n\nFix ONLY the [FAIL] items.`
    : ''

  lastImpl = await agent(
    `Act as the implementer defined in .claude/agents/implementer.md.
${context}
TASK: ${task}${correctionCtx}
When done: list created/modified files + a description of each change.`,
    { model: MODELS.implementer, label: `impl:iter${iteration}`, phase: 'Implement' }
  )
  if (!lastImpl) return crash('implementer', iteration)

  phase('Review')
  if (MODELS.reviewer.includes('/')) {
    // Provider-qualified id: a cheap seat runs the bridge in ONE foreground call and relays its stdout untouched.
    const r = await agent(
      `Run exactly this and change nothing: scripts/external-review.sh ${MODELS.reviewer}
Run it ONCE, in the foreground, with the maximum Bash timeout (timeout: 600000); it takes 2-4 minutes. Do not background it or poll it.
Return in "output" the COMPLETE stdout, character for character, without summarising or commenting.
If the command fails, return the error in "output" followed by a last line REJECTED.`,
      { model: MODELS.scout, label: `review:iter${iteration}`, phase: 'Review',
        schema: { type: 'object', additionalProperties: false, required: ['output'], properties: { output: { type: 'string' } } } }
    )
    lastReview = r?.output ?? ''
  } else {
    lastReview = await agent(
      `Act as the adversarial reviewer defined in .claude/agents/reviewer.md.
You receive ONLY artifacts — never the implementer's reasoning.
Mandate: find reasons to REJECT. Default = FAIL until there is evidence of PASS.

Implementation received:
${lastImpl}

Read harness-rubric.md and .claude/agents/reviewer.md from the repo.
Evaluate the reviewer's mandatory criteria.
Format: [PASS|FAIL] criterion — concrete evidence
Last line (no extra text): APPROVED or REJECTED`,
      { model: MODELS.reviewer, label: `review:iter${iteration}`, phase: 'Review' }
    )
  }
  if (!lastReview) return crash('reviewer', iteration)

  // The verdict is the LAST line, compared whole. A substring test reads "[FAIL] … not APPROVED"
  // as an approval, and one stray word opens the loop.
  approved = lastReview.trim().split('\n').pop().replace(/[*`_\s]/g, '') === 'APPROVED'
  log(approved ? `✓ APPROVED iter ${iteration}` : `✗ REJECTED — correcting`)
}

if (!approved) log(`⚠ Did not converge after ${maxIter} iter — escalate to the human`)

phase('Preflight')
// The runtime has no shell, so a seat runs the gate — and reports FIELDS, not prose. A substring test
// for "pass" turns "3 passed, 2 failed", "bypass", or a SKIP followed by the gate's closing PASS
// banner into a green preflight. An exit code and a list of skipped checks cannot be misread that way.
const PREFLIGHT_CMD = 'npm run preflight' // Adapt to the project's gate (detected in Step 1)
const PREFLIGHT_SCHEMA = {
  type: 'object',
  additionalProperties: false,
  required: ['exitCode', 'skipped', 'failedCheck', 'tail'],
  properties: {
    exitCode: { type: 'integer' },
    skipped: { type: 'array', items: { type: 'string' } },
    failedCheck: { type: ['string', 'null'] },
    tail: { type: 'string' },
  },
}
const preflight = await agent(
  `Run exactly this and change nothing: ${PREFLIGHT_CMD}; echo "EXIT=$?"
Report, without interpreting:
- exitCode: the number printed after EXIT=
- skipped: every output line that reports a check as skipped or not run (SKIP, skipped, ⊘, "not verified"), verbatim
- failedCheck: the check that failed, or null when exitCode is 0
- tail: the last 60 lines of output, verbatim
Do not fix anything.`,
  { model: MODELS.preflight, label: 'preflight', phase: 'Preflight', schema: PREFLIGHT_SCHEMA }
)

// A skipped check is not a passed one: exit 0 with a SKIP is NOT VERIFIED, and the handoff says so.
const skipped = preflight?.skipped ?? []
const preflightPassed = preflight?.exitCode === 0 && skipped.length === 0
const preflightState = preflightPassed ? 'PASS'
  : preflight?.exitCode === 0 ? `NOT VERIFIED (${skipped.length} skipped)`
  : `FAIL (exit ${preflight?.exitCode ?? '?'}${preflight?.failedCheck ? ` · ${preflight.failedCheck}` : ''})`
log(`Preflight: ${preflightState}`)

// The handoff is what the seats REPORT: the reviewer's [PASS|FAIL] lines are its evidence, the open
// [FAIL] lines are its blocker. Nothing in this runtime can re-run them, so the label says so.
const verdictLines = lastReview.split('\n').filter((l) => /^\[(PASS|FAIL)\]/.test(l))
const openFails = verdictLines.filter((l) => l.startsWith('[FAIL]'))
const handoff = {
  status: approved && preflightPassed ? 'complete' : approved ? 'continue' : 'blocked',
  summary: approved
    ? `Reviewer approved after ${iteration} iteration(s); preflight ${preflightState}`
    : `Reviewer still rejects after ${maxIter} iteration(s)`,
  evidence: [...verdictLines, `preflight: ${preflightState}`, ...skipped.map((l) => `preflight skipped: ${l}`)],
  ...(approved ? {} : { blocker: openFails.join(' · ') || 'reviewer returned REJECTED with no [FAIL] line' }),
}
const LABEL = 'Reported by the implementer/reviewer seats — not independently certified: '

return {
  task, iterations: iteration, approved, preflightPassed, handoff,
  nextStep: LABEL + (approved && preflightPassed
    ? 'git add -p && git commit'
    : approved && preflight?.exitCode === 0 ? 'Preflight skipped checks — supply what they need and re-run; a SKIP is not a PASS'
    : approved ? 'Preflight failed — fix before commit'
    : `Did not converge — review remaining [FAIL] after ${maxIter} iter and report to the human`),
}
```

The `handoff` the workflow returns — `status: complete | continue | blocked`, `summary`, `evidence`,
`blocker` when blocked — is the same contract `/iterate` gates with `loop-gate.js check-handoff`. Here
nothing gates it: the workflow runtime has no shell, so the handoff is what the seats say about their
own work, and `nextStep` carries the label that says so. A human reading "complete" reads a report,
not a certificate.

**Scout and Plan are a cost optimisation, not a gate.** They run once, before the loop; if either seat dies the
run continues without it. They pay off on tasks that touch several files, because the implementer stops
paying frontier prices to read the repo. On a one-file task they cost more than the implementation
(one measured run: scout + analyst ≈ 1.3× the implementer's own cost) — pass `preparer: false` there, or
use the fast path instead of this workflow. The analyst's `BLOCKER:` first line returns a `blocked` handoff
before any implementer tokens are spent.

### Step 4c — Audit skills/workflows bloat + curated recommendations (NEVER auto-install or auto-remove)

Two parts, in order: **(i) audit what exists and flag saturation** → **(ii) recommend removals and additions**. Never install or remove anything automatically. The "minimal harness" lesson is the north star — anecdotally the Vercel D0 case (−80% tools → 3× faster, an informal talk reference), and corroborated reproducibly by the `ponytail` skill's published benchmark (80–94% less code, 3–6× faster across Haiku/Sonnet/Opus; reproduce with `npx promptfoo eval`). An audit that only adds and never recommends removal is incomplete.

**Part i — audit existing skills and workflows for bloat.** Inventory the global skills folder (affects all projects), the project skills folder, and the project workflows folder. Flag if a scope exceeds its threshold:

| Scope | Threshold | Signal |
|-------|-----------|--------|
| Global skills total | > 15 | High risk of context saturation across all sessions |
| Project skills | > 5 | Agent focus degrades; likely redundancy with AGENTS.md |
| Project workflows | > 3 | Multiple workflows doing overlapping orchestration |

Classify each skill/workflow as **KEEP** (used in this repo, not covered by AGENTS.md), **REVIEW** (overlaps with another skill or with AGENTS.md), or **REMOVE** (domain not present in this repo, no role separation, no stop conditions, no `Check:` criteria, or duplicates `develop-phase.js`).

**Pre-loop-design anti-patterns** — mark any skill/workflow as a REMOVE candidate if it:
- Combines implementer + reviewer in a single agent (no role separation)
- Has no stop conditions ("keep improving until good")
- Instructs the model to be a "full assistant" without a specialized role
- Duplicates what `develop-phase.js` already does (another workflow that runs implement→review without model switching)
- Has no `Check:` criteria — pure prose instructions with no machine-verifiable outcome
- References tools or integrations not present anywhere in the repo's dependency files

**Workflow-specific check** — for each file in `.claude/workflows/`: does it assign different models per role (if not → REVIEW, it's pre-Loop-Design)? Does it have a stop condition (`maxIter` or equivalent, if not → REVIEW)? Does it duplicate `develop-phase.js` (if yes → REMOVE)?

Global skills: never recommend `rm`. Recommend per-project deactivation via a convention — list skill names in `.claude/skills-ignore` and add a line to `CLAUDE.md` instructing the model not to invoke them here. The model reads CLAUDE.md at session start and honors the list (soft, not a hard block). Project skills and workflows are local files — recommend their removal with a reason, but let the human run the delete.

### Step 5 — Emit the executable rubric (`harness-rubric.md`)

Convert every audited item into a rubric entry following [rubric-template.md](rubric-template.md): ID, criterion, `Check:` command, threshold, current state (PASS/FAIL + measured value). Write it at the repo root (ask before writing; if running read-only, output its content in the reply). Then close with the loop invocation:

> To converge: iterate until every check in `harness-rubric.md` passes **OR** 10 iterations. After each change, re-run only the affected checks; every 3 iterations, re-run the full rubric. If FAILs remain after 10 iterations, report the blockers to the human.

This is the core idea: the audit is a photo of a static report; the rubric is a **convergence target** a loop runs against.

### Step 6 — Adversarial verification of this audit

Before delivering, spawn a fresh-context subagent (read-only) following [verifier-protocol.md](verifier-protocol.md): it receives ONLY the rubric + repo path — never this audit's reasoning — re-runs the `Check:` commands of 3–5 sampled items (always include any item graded ✓ without a pasted command output), and tries to REFUTE the verdicts. For at least one PASS item, it also runs the **negative-control self-test** from verifier-protocol.md (does the check FAIL on an input it should reject? a check that can't say no is a broken thermometer → verdict INVALID). Fix every discrepancy before the final report and note `verified: N/M sampled checks confirmed` in the summary. Cheap insurance: these are `test -f` / `wc -l` commands, not deep analysis.

## Rules

- **Never inflate.** If the project is tiny (one-file script, weekend hack), say so and recommend a minimal AGENTS.md only. The minimal-harness lesson: less harness, more focus (anecdotal Vercel D0 −80% tools → 3× faster; reproducibly corroborated by ponytail's benchmark).
- **Never delete files** during an audit — read-only except `harness-rubric.md` (and ask before writing it).
- **If AGENTS.md exceeds 200 lines**, the FIRST recommendation is to trim — a bloated harness degrades the model.
- **If the project has neither tests nor lint**, push back: "verification is pillar 3, not optional. What was the project's release process before?"
- **If CLAUDE.md exists but no AGENTS.md**, the lock-in risk is the headline finding.
- **If the rubric can't say no, it isn't a rubric.** Any criterion not checkable by command gets rewritten or dropped — subjective items ("code should be clean") are banned from `harness-rubric.md`.
- **For multi-harness portability**, AGENTS.md is the canonical file. Harness-specific deltas (CLAUDE.md, .cursorrules) are secondary.
- **After every audit, distill (M4) into memory:** a new stack not covered by the recipes, a check that produced a false positive/negative, a new anti-pattern observed. One verified rule per audit beats ten raw notes — the skill itself must climb Fail→Consult between runs.
